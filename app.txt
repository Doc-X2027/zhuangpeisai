机车装配小队前端界面方案比较与一天开发规格
============================================

一、项目现状与目标

当前工程在 Windows、Python 3.12 环境运行，通过 server_multithread.py 提供 TCP 服务。
auto 流程包括图像识别、生成装配工作流、生成比赛日志三个阶段，目前由控制台三次回车控制。

前端目标：
1. 在一天内完成可用于比赛演示和操作的单窗口界面。
2. 展示任务图片、三个操作阶段、识别文本、工作流 JSON、运行日志及比赛时间。
3. 用界面按钮完全替代控制台三次回车，同时保持现有 TCP 协议和机械臂执行序列兼容。
4. 大模型调用期间界面不能卡死，图像识别结果保留逐字流式显示效果。


二、方案比较

方案一：PySide6 商业化界面

技术说明：
使用 PySide6（Qt for Python）开发现代桌面软件界面。通过 Qt 样式表实现彩色圆角卡片、按钮、
状态标签、阴影和统一主题；通过 QThread 或线程池执行耗时任务。

可行性：高
开发复杂度：中等偏高
一天完成概率：高，但必须限制为单窗口比赛版
新增依赖：需要安装 PySide6（当前环境尚未安装）

优点：
- 能实现接近商业软件的视觉效果，圆角、颜色、阴影和布局控制能力强。
- 图片、长文本、JSON、分页区和状态提示等组件成熟。
- 后台线程和界面信号机制完善，适合耗时的大模型与图像识别任务。
- 高分辨率屏幕适配和后续扩展能力较好。

缺点与风险：
- PySide6 安装包较大，比赛电脑需要提前完成依赖安装。
- 必须正确处理 GUI 主线程和后台任务线程，否则可能出现界面无响应。
- 一天内不适合加入复杂动画、多页面导航、账号系统或完整配置中心。

适用场景：
适合正式比赛展示、现场操作及后续持续扩展。


方案二：Tkinter 简单界面

技术说明：
使用 Python 自带的 Tkinter/ttk 开发基础桌面界面，使用 Pillow 显示图片，通过 threading
执行耗时任务，并使用 after() 将后台结果安全更新到主线程。

可行性：很高
开发复杂度：低
一天完成概率：很高，基础版本约半天可以完成
新增依赖：无需新增 GUI 依赖；当前环境已安装 Tkinter 和 Pillow

优点：
- Python 自带，部署简单，安装风险最低。
- 适合快速实现图片、按钮、文本框、进度和状态标签。
- 代码量较少，出现问题时容易定位和修复。

缺点与风险：
- 默认控件外观偏传统，较难达到商业软件质感。
- 圆角卡片、阴影、动画和复杂主题需要额外绘制，反而会增加维护成本。
- 页面扩展、复杂布局和高分辨率显示效果弱于 PySide6。

适用场景：
适合作为内部工具、功能验证版本或 PySide6 无法安装时的比赛保底方案。


核心指标对比

指标                PySide6 商业化方案             Tkinter 简单方案
------------------------------------------------------------------------
视觉效果            优秀，适合比赛展示             一般，偏工具化
彩色圆角界面        原生样式能力强                 需要额外绘制或近似实现
开发复杂度          中等偏高                       低
预计开发时间        7～8小时                       4～5小时
一天完成风险        可控，需严格限制范围           很低
新增依赖            PySide6                        无新增 GUI 依赖
后台任务支持        QThread/线程池与信号机制成熟    threading + after()
长期扩展性          高                             中等偏低
比赛展示效果        最佳                           可用


三、推荐结论

推荐采用方案一：PySide6 商业化界面。

选择原因：
1. 项目用于比赛，界面的清晰度、专业感和状态反馈比减少少量代码更重要。
2. 用户接受安装 PySide6，并明确要求彩色、圆角、图片及完整文本同时展示。
3. 只开发单窗口比赛版时，PySide6 可以在一天内完成。
4. Qt 的后台任务与信号机制更适合现有大模型调用，能降低界面卡死风险。

若比赛电脑无法及时安装或验证 PySide6，则使用 Tkinter 作为保底方案，不改变核心业务接口。


四、推荐界面规格

1. 整体结构

- 单窗口，建议初始尺寸 1280×800，支持最大化和自适应缩放。
- 使用深蓝或深灰背景，搭配蓝、青、橙等状态色；所有内容放入圆角卡片。
- 顶部显示“机车装配小队智能装配系统”、服务器状态、工程开始时间和持续时间。
- 左侧为任务图片预览区，图片等比例缩放，不拉伸变形。
- 右侧为三个阶段操作区和当前阶段状态。
- 底部为结果分页区，包含“识别结果”“工作流 JSON”“运行日志”三个标签页。

2. 三阶段按钮

- 按钮一：开始图像识别。
- 按钮二：生成装配工作流。
- 按钮三：生成比赛日志并下发执行序列。
- 初始仅启用按钮一；当前阶段成功后解锁下一按钮。
- 阶段运行时禁用重复点击，并显示“处理中”状态或进度动画。
- 阶段失败时显示清晰错误信息，只允许重试当前阶段，不清空已成功结果。
- 第三阶段成功后显示日志路径和最终执行序列。

3. 信息展示

- 识别结果逐字追加到文本框，保留流式文本效果，并自动滚动到最新内容。
- 工作流 JSON 在界面中使用格式化缩进和语法配色，比赛日志中仍保存紧凑单行 JSON。
- 日志区显示关键事件、时间和错误，不重复输出无意义的调试信息。
- 图片加载失败、模型失败、JSON 无效及日志写入失败都必须在界面中可见。


五、实现架构与数据流

1. 将 server_multithread.py 中 auto 分支的三个阶段拆成可单独调用的业务函数：
   identify_stage()、workflow_stage()、log_stage()。
2. GUI 与服务端在同一台电脑、同一进程运行，避免增加新的远程控制协议。
3. TCP 监听和大模型调用都放入后台线程，Qt 主线程只负责界面事件和绘制。
4. 后台任务通过 Qt 信号发送阶段状态、文本片段、错误、JSON 和最终执行序列。
5. GUI 按钮代替 input()；不再让工作线程等待控制台输入。
6. 保持 planning、identify、auto 命令及客户端最终收到的执行序列兼容。
7. 固定覆盖“机车装配小队比赛文档日志.txt”，并继续记录工程开始时间和持续时间。


六、一天开发安排

第1小时：环境和业务拆分
- 安装并验证 PySide6。
- 将 auto 三阶段从控制台 input() 中拆出，保留现有业务结果。

第2～3小时：主界面
- 完成顶部状态区、圆角卡片、任务图片区、三个阶段按钮和底部分页区。
- 完成颜色、字体、间距及窗口缩放规则。

第4～5小时：线程与业务接入
- 接入图像识别、工作流生成、日志生成和 TCP 服务。
- 实现按钮顺序、后台线程、状态信号及异常处理。

第6小时：结果展示
- 接入流式识别文本、JSON 展示、日志展示、开始时间和持续时间。

第7小时：视觉优化
- 统一圆角、阴影、按钮状态、成功/警告/失败颜色和提示文案。

第8小时：比赛测试
- 完整运行三阶段流程。
- 测试重复点击、接口失败、图片缺失、JSON 错误及窗口关闭。
- 在实际比赛电脑和显示器分辨率下试运行。


七、验收标准

1. 启动应用后无需操作控制台即可完成全部三个阶段。
2. 界面同时展示任务图片、阶段按钮、识别文本、JSON、日志和时间信息。
3. 模型和图像任务运行时窗口可拖动、切换标签页且不会无响应。
4. 三个阶段必须按顺序执行，重复点击不会启动重复任务。
5. 识别文字具有可见的逐字流式效果。
6. 成功生成并覆盖“机车装配小队比赛文档日志.txt”。
7. 原有 TCP 客户端仍能连接，最终执行序列格式不变。
8. 所有错误均在界面显示，失败阶段可以重新执行。


八、范围限制

一天版本只包含单窗口比赛界面，不包含账号登录、多语言、在线更新、复杂动画、数据库、
多套主题和完整配置中心。首日不强制打包 EXE；若功能和测试提前完成，再使用 PyInstaller
进行打包验证。
